# A11y Scan Baseline — 2026-08-03

Target: chat widget + test harness at `http://localhost:8000/widget/test_page.html`,
panel OPEN for all instruments. Standard: WCAG 2.1 AA (Best Practices on).
Method: four predictions registered before any instrument ran; observations
recorded before verdicts; instruments treated as judge columns, not ground
truth. Four instruments: two automated (Lighthouse, axe DevTools), two manual
(keyboard walk, VoiceOver). This file is the pre-fix baseline; the fix
session's re-scan is graded as a delta against it.

## Pre-registered predictions
- **P1** — no `aria-live` on the message container: screen readers will not
  announce bot replies.
- **P2** — no `role="dialog"` on the panel: reads as a generic div to
  assistive tech.
- **P3** — no focus management: focus does not enter the panel on open,
  Escape does not close, focus does not return on close.
- **P4** — placeholder used as the input's only label: automated tooling
  flags a missing label. *(Instrument-behavior half of this prediction was
  wrong — see grades.)*

## Instrument 1 — Lighthouse (Accessibility category, Snapshot mode)
Config: Snapshot mode deliberately — Navigation mode reloads the page, which
collapses the panel and silently audits the closed state (wrong denominator).
Two captures: 2:03 PM and 2:19 PM (re-run to expand audit lists).

Results: 12/14. Failures, both on the harness shell, neither on widget code:
1. `<html>` element missing `[lang]` attribute
2. Document has no main landmark

Passed (widget-relevant): form-element labels, button accessible names, color
contrast, touch-target size, heading order. Not Applicable: 49.

Scope adjudication: "Form elements have associated labels" and "Buttons have
an accessible name" both SCORED as passes. The harness contains no form
controls — the only input on the page lives inside the widget panel, and
hidden elements are not audited. A scored label audit therefore proves a
visible input existed at capture: **widget in scope, panel open.**

N/A-list-as-evidence: "Elements with `role="dialog"` have accessible names"
sits in Not Applicable — that audit runs whenever a dialog role exists, so
N/A proves **no dialog role anywhere in the DOM** (P2 evidence).

Label-audit caveat: the pass is explained by the accessible-name computation
treating `placeholder` as a last-resort fallback. The automated floor sits
below the practice bar; see P4.

## Instrument 2 — axe DevTools extension (2:28 PM)
Config: WCAG 2.1 AA, Best Practices ON, axe-core latest, Experimental OFF,
Balanced confidence. Telemetry, AI data sharing, AI features, and shared
screenshots disabled before scanning. Site access granted to
`http://localhost:8000` only (minimal grant).

Results: 7 automatic issues — 0 critical / 1 serious / 6 moderate; 6 of 7
best-practice tier.

| Rule | Count | Impact | Tier | Elements |
|---|---|---|---|---|
| `<html>` must have lang attribute | 1 | serious | **WCAG 2.1 A (3.1.1)** | harness `<html>` |
| Document should have one main landmark | 1 | moderate | best-practice | harness `<html>` |
| All content contained by landmarks | 5 | moderate | best-practice | harness `h1`, `p`; widget `#aby-header`, `#aby-msgs`, `#aby-input` |

The lang failure is the **only true WCAG conformance violation either scanner
found on the entire page** — and it belongs to the test harness, not the
widget.

Element snippets as evidence (captured live DOM, verbatim):
```
<div id="aby-msgs"><div class="aby-msg aby-bot">Hi! I'm the Nextdoor
Neighbor, American Backyard's assistant. ...</div></div>
```
No `aria-live`, no `role` — **P1 confirmed at the markup level.**
```
<input id="aby-input" placeholder="Ask about products, delivery, store
operations, or more..." maxlength="2000">
```
No `aria-label`, no `title`, no associated `<label>` — **P4 confirmed from
source**: the placeholder is the input's only naming mechanism, which is
exactly what satisfies both engines' automated label rule via accname
fallback. (Side receipt: `maxlength="2000"` matches the server's
`ChatRequest` bound — client and server agree on the contract.)

## Instrument 3 — Keyboard walk (mouse untouched, fresh load)
- **(a) FAIL** — Tab never lands on the launcher with a visible focus ring;
  the ring alternates with browser UI. From inside the panel, one *invisible*
  stop occurs before focus reaches the browser — suspected: the Send button
  receiving focus with no visible indicator (WCAG 2.4.7 candidate;
  disambiguator open below).
- **(b) FAIL** — Enter and Space do not open the panel.
- **⇒ WCAG 2.1.1 Keyboard (Level A): the widget cannot be opened without a
  mouse. A keyboard-only user is fully excluded from the product. Gravest
  finding of the audit.**
- **(c) FAIL** — after mouse-open, focus does not move into the panel.
- **(d) FAIL** — no perceivable tab order inside the panel.
- **(e) PASS** — Enter in the input sends the message (sole green).
- **(f) FAIL** — Escape does not close the panel.
- **(g) MOOT** — no keyboard close path exists, so focus-return is untestable.

Open disambiguator (sharpens (a)/(d), does not change the verdict): type in
the input, press Tab once, press Enter. Message sends ⇒ Send held focus
invisibly (CSS fix); nothing happens ⇒ focus left the widget (tab-order fix).

## Instrument 4 — VoiceOver
- **Q1 (input announcement):** not captured during the session; superseded —

  quote.
- **Q2 (reply arrival): SILENT.** With VoiceOver running, a bot reply
  rendered and nothing was announced. **P1 confirmed experientially.**
- **Q3 (buttons):** Send announced as "Send, button" — accessible name

## Prediction grades
- **P1 — CONFIRMED** at both levels: markup (bare `#aby-msgs`) and
  experience (VO silence on reply).
- **P2 — CONFIRMED** by two engines, both by absence (Lighthouse N/A
  placement; no axe dialog findings because no dialog exists).
- **P3 — CONFIRMED AND EXCEEDED.** Registered as missing focus management;
  observed as total keyboard exclusion (2.1.1 Level A) plus invisible focus
  indicators (2.4.7 candidate). Only Enter-to-send survived.
- **P4 — CONFIRMED in substance, wrong in instrument behavior.** The input
  is placeholder-only (DOM-proven), but the registered claim that automated
  tooling would flag it was incorrect: both engines' label rule accepts the
  placeholder accname fallback. Rubric error logged against the auditor.

## Findings ledger → fix session
Widget (5):
1. Launcher → real `<button>` with accessible name — **removes the 2.1.1
   Level A blocker.**
2. Panel → `role="dialog"` + `aria-label` — clears P2 *and* all three widget
   landmark-containment findings (dialog content is exempt from the region
   rule).
3. `#aby-msgs` → `aria-live` — clears P1.
4. Input → programmatic label; placeholder demoted to hint — clears P4.
5. Focus management: focus input on open; Escape closes and returns focus to
   launcher; visible focus indicators — clears P3 / 2.4.7.

Harness (2):
6. `<html lang="en">`; wrap page content in `<main>` — clears the lang
   violation, the main-landmark finding, and both harness containment
   findings.

Verification plan: re-run Lighthouse Snapshot and axe with identical configs,
repeat keyboard walk a–g and VoiceOver Q2. The delta against this baseline is
the receipt.

## Method notes & limitations
Both automated tools disclaim subset coverage, and this audit demonstrated
the point: the scanners' gravest finding was a missing `lang` attribute on
the harness, while ninety seconds of manual testing found a Level-A failure
that excludes an entire class of users. Automated green is not accessibility.
One verification grep during the session ran with eaten escape characters,
producing guaranteed-empty output that mimicked a pass — retired, superseded
by DOM evidence; noted as a transcript-channel failure mode. WCAG 2.1 AA is
the working target; conformance is ultimately a human and legal judgment,
not a scan result.
